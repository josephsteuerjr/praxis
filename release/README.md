# Сборка и проверка Hélène

Нужны Git, Python 3.11 или новее, свободное место под исходники, донор и распакованные инструменты. Команды запускаются из корня исходников. В Windows команда Python может называться `py -3.11`, в Linux и macOS — `python3`. Для восстановления из ZIP начните с [START-HERE.md](../START-HERE.md).

1. В отдельной рабочей копии измените код. Версию во фронтах, lock-файлах, установщике и нативных пакетах меняет `python release/kit.py prepare 2.9.1`. Просмотрите `git diff`, запустите проверки затронутых компонентов и закоммитьте изменение. Номер здесь служит примером.
2. Выполните `python release/kit.py source --out ../out`. В общем каталоге результата получается `Helene-<версия>-source.zip`. Архив строится из Git-объектов, включает режимы файлов и данные для восстановления точного коммита. Профиль пользователя в состав исходников не входит.
3. Для Windows x64 выполните `python release/kit.py build --target windows-x86_64 --cache ../downloads --out ../out`. Та же команда принимает `debian-x86_64`, `fedora-x86_64`, `macos-x86_64`, `macos-arm64` и `server-linux-arm64`. Настольную сборку выполняйте на нативной системе указанной архитектуры, Linux — в соответствующем дистрибутиве. Серверный ZIP можно подготовить на настольной системе; его запуск проверяют отдельно на Linux ARM64.
4. Предыдущие опубликованные ZIP, размеры, SHA-256, URL и платформы перечислены в [inputs.json](inputs.json). Перед следующей сменой базы перенесите в манифест данные проверенных активов издателя. Файлы можно заранее положить в `--cache` под указанными именами. При сборке используются только ZIP с ожидаемыми размером и хешем. Node, npm, кэш платформенных пакетов, Python, нативные компоненты, реле и их лицензии находятся в соответствующем доноре. Внутренние описи — `verification/manifest.json`, `python-package-files.json` и `relay-product/BUILD-PASSPORT.json`. ARM-сервер несёт собственный паспорт ELF. При смене нативной зависимости сначала квалифицируйте новый донор.
5. Комплект извлекает инструменты во временную папку и собирает пять фронтов из lock-файлов командой `npm ci --offline`, затем `npm run build`. Ядро составляется из текущих `praxis/` и `helene/core/`. Сборщик сверяет реальные исходники и выходы, ведёт опись архива и сохраняет SHA в `<target>.json`. Завершённую сборку можно вызвать повторно. При частичном результате или смене коммита возьмите новый `--out`. Для сквозной проверки запустите приложение с чистым тестовым профилем на каждой целевой ОС.
6. Соберите ZIP и квитанции от нативных сборщиков в общем `--out`. Для локальной публикации одного результата выполните `python release/kit.py publish --out ../out --target windows-x86_64 --to ../test-channel`. Повторите аргумент `--target` для каждой платформы. В каталоге версии появятся выбранные активы и `SHA256SUMS`. Для GitHub заранее создайте проверенный тег в своём репозитории и передайте `--github-draft OWNER/REPO`. Авторизация берётся из настроенного издателем GitHub CLI. Команда создаёт черновик. После тестового обновления издатель проверяет состав черновика, выбирает видимость и момент публикации в GitHub.

Изменение Python удобно проверить в копии программы её интерпретатором. Для проверки окна внесите в `desk/app/src/main.ts` различимую DOM-метку, соберите тестовую версию и найдите метку в JS по адресу `Helene/app/static/` внутри ZIP. Сохраните SHA исходника и выходного JS. Для проверки обновления используйте копию предыдущей программы и тестовый канал с хешами полученных активов.

При локальной публикации команда записывает также GitHub-совместимый release.json. Запустите в каталоге тестового канала python -m http.server 8765 --bind 127.0.0.1 и передайте апдейтеру URL http://127.0.0.1:8765/v<версия>/release.json. Для другого адреса укажите --channel-url при публикации. Штатная CI-задача «Build Hélène platform candidate» принимает платформу при ручном запуске, сохраняет ZIP и квитанцию в Actions artifacts. Для квалификации запуска ARM архив надо отдельно испытать на ARM64.
