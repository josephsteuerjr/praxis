# Stop / update / resume — source correction 01.10

После обновления 1.2.8 у владельца исчезла служба: установщик снял старую
регистрацию, но при owner stop пропустил установку новой. Конфиг оставил службу
владельцем lifecycle, поэтому окно правильно не подняло запасной движок.

## Изменения

- Windows setup регистрирует службу и session task при активном owner stop.
  Служба остаётся keeper; существующие проверки marker в службе/session-host
  запрещают подъём детей. Установщик не снимает marker.
- Abort восстанавливает снятую службу до проверки запрета запуска окна.
- CLI resume загружает и проверяет конфиг. Для service-owned установки сначала
  проверяет наличие задачи, доступность SCM и Running службы (ожидание до 5с).
  Лишь затем снимает autonomy pause и owner stop, проверяет результат task Run.
  Ошибки до снятия stop сохраняют его. Ошибка запуска после снятия возвращает
  ненулевой код и прямо говорит, что запрет уже снят, но запуск не подтверждён.
- Для установки без службы resume не требует task и оставляет запуск окну.
- Журнал окна сообщает о владельце lifecycle по конфигу, а не выдумывает Running.
- При отказе команды окно различает сохранённый stop и снятый запрет без
  подтверждения запуска, вместо общего сообщения только о правах/процессе.

Успех task Run означает принятую просьбу, а не готовый reader/API. Проверки
готовности в продукте по-прежнему обязательны. Регистрация службы может сообщить
отдельное предупреждение о неудаче создания задачи; эта прежняя политика не менялась.
Resume в таком случае откажет до снятия stop.

## Проверки

Изолированный Rust test binary из svc/src/resume.rs: 5/5. Проверены отсутствие
инфраструктуры, отказ снятия pause, отказ снятия stop, отказ task Run после снятия
stop и успешный порядок действий. Ни SCM, ни marker, ни реальные процессы агента
тесты не трогают. Модуль входит и в обычный cargo test svc.

Windows cargo check прошёл для svc, shell и setup; shell/setup с
--features custom-protocol. Остались прежние предупреждения dead_code.
git diff --check чист. Полная release-сборка/установщик здесь не создавались.

Это не доказательство полного функционального stop/update/resume на Windows.
Живая установка не обновлялась, служба и работающий агент не останавливались.

## Следующая приёмка — изолированная Windows VM

1. Установить известную рабочую поставку со службой, проверить identity API и ответ.
2. Остановить владельцем; сохранить содержимое marker; дождаться отсутствия reader.
3. Обновить кандидатом: marker неизменен, SCM и session task зарегистрированы,
   reader отсутствует и после нового входа пользователя.
4. Явно resume: marker снят, SCM Running, один reader, корректная identity API,
   реальный ответ. Проверить также установку без службы.
5. Повторить stopped update с отменой/ошибкой после снятия прежней службы:
   прежняя регистрация возвращена, marker сохранён, читатель не стартует.
6. В тестовой VM убрать task либо службу: resume возвращает ошибку и сохраняет
   marker. Отдельно проверить отказ task Run после успешного preflight.
7. Полный rollback поставки, данных и внешних ресурсов остаётся отдельным gate.

Не использовать для этого рабочую установку владельца и не принимать unit PASS
за прохождение этих шагов. Старый v1.2.8 не перепубликовывать.
