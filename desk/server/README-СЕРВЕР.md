# Hélène на сервере: перенос агента и запуск в Docker

Агент живёт в одной папке `data/`. Перенос — это архив этой папки с
настройками; на сервере он разворачивается в такой же контейнер, что и на
Windows, только без оболочки: канал и раннер держит `server/serverboot.py`, а
окно на ПК подключается к серверу по адресу и ключу. Обратный перенос
сервер → ПК — тем же архивом.

## Коротко: одна команда, дальше — одна кнопка

На сервере нужен только Docker (с compose). Скачай поставку `Helene-<версия>.zip`
(GitHub → Releases) на сервер, распакуй и запусти от root:

```bash
unzip -q Helene-<версия>.zip
sh Helene/server/install.sh                          # поставить Hélène или обновить ту, что стоит
sh Helene/server/install.sh helene-<агент>-<штамп>.zip   # …и перенести агента с ПК (архив из окна)
```

Команда всё делает сама:

- **стоит Hélène** (в том числе старая, до 1.1.1) — находит её по контейнеру агента,
  поднимает рядом исполнителя обновлений и просит его обновить. Он делает копию,
  переносит правки агента в его собственном коде — и те, что жили внутри старого
  контейнера, — запускает новую версию, проверяет её, а не заработает — возвращает
  прежнюю сам. Память агента не трогается;
- **не стоит** — кладёт Hélène в `/opt/helene` (другое место — `HELENE_DIR=…`),
  разворачивает агента из архива, если он дан, запускает и печатает ключ для окна;
- закрывает папку установки от других пользователей сервера.

Имя сайта, по которому окно ходит к серверу (если оно есть), — один раз, при первой
установке: `HELENE_HOSTS=helene.example.com sh Helene/server/install.sh`.

**Дальше обновления — без сервера:** кнопкой «Обновить» в окне (Система → Обновление)
или просто словом агенту — «обновись». Агент может и сам предложить обновиться; тогда
хватит «да». Повторный запуск команды ничего не ломает: она поднимет то, что стоит, и
скажет, какая версия.

Ниже — как это устроено и как то же самое сделать руками.

## 1. Экспорт на ПК

Настройки → карточка «Перенос» → «Экспорт агента», либо без окна:

```powershell
& "$env:LOCALAPPDATA\Programs\Helene\helene-setup.exe" --export --quiet
```

(`helene-setup.exe --export` находит установку по записи в реестре и зовёт
тот же помощник; путь к архиву — в `export.log` рядом с установщиком.) Или
напрямую:

```powershell
& "$env:LOCALAPPDATA\Programs\Helene\runtime\python.exe" "$env:LOCALAPPDATA\Programs\Helene\app\localharness\carry.py" export --config "$env:LOCALAPPDATA\Programs\Helene\helene.json"
```

Получается `helene-<агент>-<штамп>.zip` рядом с `helene.json`. **Внутри —
ключ модели, токен бота, вход ChatGPT и сессия Telegram** (иначе агент на новом
месте нем); паспорт `helene-carry.json` в архиве перечисляет их поимённо. Архив
не для пересылки посторонним. Что не едет: `data/body/` (тело руки `computer`
принадлежит машине), журналы, замок дерева, ключ окна, стыки `workspace/mnt/`.

## 2. Сервер: поставка и архив (руками)

То же, что делает `install.sh`, по шагам. На сервере нужны Docker и Compose. Папка
проекта — своя, например `/opt/helene`:

```bash
mkdir -p /opt/helene && cd /opt/helene
unzip -q ~/Helene-<версия>.zip && mv Helene/* . && rmdir Helene   # та же поставка, что и на Windows
cp server/helene.server.json helene.json
python3 app/localharness/carry.py import --config helene.json --archive ~/helene-<агент>-<штамп>.zip
```

Импорт разворачивает `data/` и сливает `helene.json`: из архива берутся блоки
агента (`agent`, `owner`, `model`, `telegram`, `relay`, `env`, `update`), а
местными остаются блоки хоста (`mode`, пути, `port`, `agent_mode`, `sandbox`,
`service`, `computer`, `phone`). На сервере ограда — сам контейнер, поэтому
`agent_mode` там `interactive`; тела руки `computer` нет; `phone.enabled: true`
— страница телефона тем же каналом.

**Подписка ChatGPT переезжает вместе с агентом.** Реле едет в поставке вторым
бинарём — `helene-relay` (Linux, рядом с виндовым `helene-relay.exe`), — а
`server/serverboot.py` поднимает его третьим ребёнком, когда в конфиге стоит
`relay.enabled`. Вход (`data/relay/local_auth`) приезжает в архиве переноса и
ложится туда, где реле его ищет; порт берётся из `relay.port`, ключ петли — из
`model.key`. Реле слушает только `127.0.0.1` и живёт В ТОМ ЖЕ контейнере, что
и харнесс, поэтому `model.base_url` вида `http://127.0.0.1:5011` из архива
верен на сервере без единой правки. Логи реле — `data/relay/logs/relay.log`,
вывод процесса — `data/relay.log`.

Чего в поставке нет — того `serverboot` не скрывает: собранная без докера
поставка приезжает без Linux-бинаря реле, и в логе контейнера при старте
стоит «relay.enabled, но реле рядом нет — агент с подпиской ChatGPT будет
нем». Собирается он одной командой на машине сборки:
`python installer/relay_src.py --build-linux`.

## 3. Запуск

```bash
cd /opt/helene
HELENE_PUBLIC_URL=https://helene.example.com HELENE_HOSTS=helene.example.com \
HELENE_MODELS=/opt/praxis-models \
docker compose -f server/docker-compose.yml up -d --build
docker logs helene | head -20     # строка ключа окна печатается при старте
```

Проект compose зовётся `helene` (поле `name:` в файле): на общем сервере
compose без явного имени берёт имя папки и считает чужие контейнеры своими
«сиротами». Никогда не запускать с `--remove-orphans` и не делать
глобальных `prune`.

Канал слушает `127.0.0.1:8094` хоста. В мир её выпускает Caddy владельца —
одна строка в его `Caddyfile`, без правки чужих маршрутов:

```
helene.example.com {
    reverse_proxy 127.0.0.1:8094
}
```

и `caddy reload` (не `restart`). Или Tailscale: тогда `HELENE_HOSTS` — имя
машины в `*.ts.net`, и канал пускает его сам.

STT: контейнер получает те же `PRAXIS_STT_*`, что у Праксис, и модель
`faster-whisper-large-v3-turbo` (int8) из тома `/models` (`HELENE_MODELS` —
папка на хосте с `audio/whisper/faster-whisper-large-v3-turbo`). Модель
грузится при первой голосовой; `HELENE_STT_KEEP_LOADED=1` держит её в памяти
(~1,6 ГБ). Без модели голосовые не расшифровываются, дерево говорит об этом
само. На Windows STT нет намеренно.

## 3.1 Управление из окна: перезапуск и журналы

Экран «Система» в окне (и в издании к серверу) показывает надзор сервера как он есть:
кто держит харнесс, какие дети подняты, с какими pid, сколько раз падали, —
и даёт три кнопки: перезапустить агента, реле или весь харнесс. Плюс хвосты
журналов (`runner.log`, `deskapp.log`, `relay.log` и собственный журнал реле) —
то же, что `docker logs`, только без ssh.

Как это устроено: канал КЛАДЁТ просьбу в `data/memory/.state/supervisor-request.json`,
надзор берёт её раз в три секунды, исполняет и пишет расписку рядом
(`supervisor-receipt.json`); он же каждые три секунды пишет о себе
`supervisor.json`. Окно считает управление доступным ТОЛЬКО по свежести этой
записки — то есть по реальности, а не по конфигу: если надзор молчит, кнопок
нет и сказано, сколько секунд он молчит.

«Перезапустить весь харнесс» в контейнере — это выход надзора; поднимает его
обратно сам Docker (`restart: unless-stopped`), окно на несколько секунд теряет
связь. Контейнер агента сам себя не пересобирает, и доступа к докеру хоста у
него нет и не будет — это была бы не кнопка обновления, а отмычка. Обновляет
сосед снаружи — исполнитель, раздел 3.2.

## 3.2 Обновление: исполнитель рядом с агентом

Агент живёт внутри контейнера, который при обновлении надо заменить, — изнутри
ему нечем. Поэтому рядом живёт исполнитель обновлений: свой маленький контейнер
(`helene-updater`) со своим доступом к докеру. Поднимает его `install.sh`; руками — из
папки установки:

```bash
cd /opt/helene
docker compose -f server/updater/docker-compose.yml up -d --build
```

Установка не в `/opt/helene` — назови путь, ТОТ ЖЕ, что на хосте:
`HELENE_DIR=/srv/helene docker compose -f server/updater/docker-compose.yml up -d --build`.
Исполнитель сверяет это сам по меткам контейнера агента и при расхождении не
работает, а говорит почему (в окне и в `docker logs helene-updater`).

У исполнителя есть и команды для самого сервера (их зовёт `install.sh`):
`docker exec helene-updater python3 /opt/helene/server/updater/updater.py status | plan <версия> | watch`.

**Код агента — на диске сервера.** `tree/` и `app/` смонтированы в контейнер из
папки установки (как у Праксис её `/opt/praxis`), а не запечены в образ: агент правит
себя (навык `my-own-code`), и правка переживает пересборку контейнера. Образ несёт
только Python и библиотеки.

Как идёт обновление:

1. **Просьба и «да».** Проще всего — одно действие владельца, оно и есть «да»:
   кнопка «Обновить до X» в окне (Система → Обновление), слово агенту «обновись» (рука
   `update_request` передаёт его слова дословно и только в ходе, который начал сам
   владелец) или команда `install.sh` на сервере. Агент может и сам попросить
   обновиться — тогда просьба ждёт согласия: «Обновить» в окне или «да» ему в чате;
   через сутки без ответа истекает. **Честно о границе:** согласие — это файл в папке
   агента, и агент своим shell может положить его и сам (рука так не сделает, но shell —
   не рука). Поэтому исполнитель и умеет ровно одно: официальный выпуск новее стоящего —
   с копией, переносом правок, испытанием и откатом; каждый его шаг виден в окне и в
   `docker logs helene-updater`.
2. **Сверка.** Исполнитель сверяет официальный выпуск — версия новее текущей, архив,
   sha256, хватит ли места на копию — и смотрит, правил ли агент свой код: сравнивает
   `tree/` и `app/` с ЧИСТЫМ исходником стоящей версии (из своего кэша, а в первый раз —
   скачав её выпуск). У старой установки, где код жил внутри контейнера, правки видны
   по `docker diff`. Окно показывает всё это под «Подробнее».
3. **Исполнение.** Скачать и сверить архив → собрать новый образ рядом (агент
   работает) → прорепетировать расширения владельца (в запертом контейнере: без сети,
   только чтение, с потолком памяти и процессов) → отложить прежнюю поставку и положить
   новую; своё владельца в папках поставки — модели в `server/models`, `server/.env`,
   свой `*.override.yml` — переезжает в новые папки (жёсткими ссылками, без копирования
   гигабайт) → дождаться конца хода агента → остановить → у старой установки (код в
   контейнере) — снимок контейнера образом отката и его код наружу → скопировать `data/` →
   **перенести правки агента**: файл, который выпуск не трогал, — как был у агента
   (и с его битом исполнения); тронутый обоими — трёхсторонним слиянием; не легло — в
   новой версии стоит вариант выпуска, а вариант агента со всеми сторонами и
   объяснением ложится ему в `data/workspace/update-<версия>/` → поднять новую версию с
   теми же адресом, портом, именами хостов, моделями и теми же файлами compose (если
   агент поднят ещё и с твоим override из `server/` — с ним же) → проверить: контейнер
   держится, канал отвечает, версия новая, надзор бьётся, агент жив, настройки и модели
   на месте, код — с диска.
4. **Испытание.** Механика прошла — агент получает записку и сам проверяет себя:
   думает ли, помнит ли, живы ли руки, расширения и перенесённые правки. Отвечает
   «принимаю» или «сломано» (рука `update_request`, `accept`/`reject`); владельцу делать
   ничего не нужно, но можно сказать своё слово поверх — кнопками «Всё хорошо» / «Вернуть
   прежнюю» в окне. «Сломано» или молчание до срока (по умолчанию 30 минут; занятому ходом
   агенту срок продлевается, но не больше чем вдвое) — откат. Мозг не настроен —
   испытание пропускается, и об этом сказано в итоге.
5. **Откат.** Прежние код и образ — и правки агента в коде такие, какими были до
   обновления. Память агента (`data/`) и `helene.json` откат НЕ трогает: переписка,
   дневник и настройки за время новой версии — тоже его жизнь. Копии `data/` и
   `helene.json` идут в дело, только если прежняя версия на данных новой не поднимается
   (тогда то, что записала новая, — рядом, не стёрто). Правки, которые агент успел
   сделать в коде новой версии (на испытании), откат отдаёт ему в
   `data/workspace/update-<версия>/after-update/`, а рядом с материалами переноса кладёт
   `ROLLBACK-<время>.md` — что переход не состоялся.
   У старой установки откат поднимает контейнер из его снимка — с правками агента,
   какими они были.
6. **Отчёт.** Итог — одной фразой простыми словами (в окне сверху; подробности —
   под «Подробнее»). Поднявшись после отката или приняв обновление, агент рассказывает
   владельцу, что вышло, — тоже просто (упавший ход по записке повторяется — до трёх раз).

Перезапуск исполнителя посреди любого шага не бросает обновление: состояние пишется
до каждого шага, который трудно отменить, и после перезапуска исполнитель доводит
начатое сам — сверку отменяет словами, подготовку возвращает, подмену до остановки
агента отменяет без его перезапуска, после — откатывает или доводит проверки. Откат,
который не выходит, он повторяет раз в минуту; после трёх неудач — итог «нужен человек»
с путём к копиям.

Что исполнитель не делает по построению: ставит только официальный выпуск
(адрес — в его compose-файле, не в `helene.json`, который правит агент) и только
новее текущего (стоящая версия — по паспорту `helene-build.json` в корне установки; нет
паспорта — отказ, а не «любая»); трогает только контейнер агента и его compose-проект;
`data/` и `helene.json` не переписывает (кроме случая выше); кода из `tree/` и `app/`
не исполняет (они теперь на диске агента — протокол у исполнителя свой,
`server/updater/protocol.py`). Копии — `/opt/helene/.updater/backups/<время>/`
(последние две; `HELENE_UPDATE_KEEP` меняет число), чистые исходники двух последних
версий — `/opt/helene/.updater/pristine/`, образы отката —
`helene-helene:helene-rollback-<время>`. `runtime/` (встроенный Python для Windows)
серверу не нужен: исполнитель его не распаковывает и не трогает.

**Папка установки закрыта** (`chmod 700`, это делает `install.sh`). Агент в контейнере —
root, а `data/`, `tree/` и `app/` смонтированы на запись: файл с битом setuid, положенный
агентом, на хосте тоже setuid, и воспользоваться им мог бы другой пользователь хоста.
Этот класс был и раньше (с `data/`); закрытая папка его снимает. Ставил руками — закрой
сам: `chmod 700 /opt/helene`.

**Подлинность выпуска держится на GitHub.** Сумма sha256 берётся из того же выпуска,
что и архив: это защита от битого скачивания, а не подпись. Взломанный репозиторий
выпусков означал бы чужой код на хосте — с «да» владельца, но всё же. Подпись выпусков
(ключ, закреплённый у исполнителя) — пока не сделана.

Руками по-прежнему можно: распаковать новую поставку поверх (`app/`, `tree/`,
`server/`) и `docker compose -f server/docker-compose.yml up -d --build` с теми же
переменными, что при установке. ⚠ Распаковка поверх затирает правки агента в его
коде (а у старой установки пересборка стирает и те, что жили внутри контейнера) —
если он их делал, обновляй `install.sh` или кнопкой.

### Со старой версии (до 1.1.1) — той же командой

До 1.1.1 код агента жил внутри образа, и правки агента лежат в слое контейнера. Отдельного
перехода не нужно: `sh Helene/server/install.sh` из новой поставки поднимет исполнителя, а
он снимет правки агента из контейнера (по `docker diff`, снимком контейнера и копией кода),
перенесёт их на новую версию и дальше будет держать код агента на диске сервера.

## 4. Окно на ПК — к серверу

В `helene.json` на ПК (Настройки → «Перенос» → «Подключить к серверу» или
руками):

```json
{ "mode": "remote", "base": "https://helene.example.com", "key": "<ключ из docker logs>" }
```

После перезапуска окно ходит в серверный канал; своих детей оболочка не
поднимает. Телефон — тот же адрес, `/m/`, спаривание по QR из окна. Вернуться
к локальному агенту — `"mode": "local"` (карточка «Перенос» делает это одной
кнопкой).

## 5. Обратный перенос

На сервере: `python3 app/localharness/carry.py export --config helene.json`,
архив — на ПК, там Настройки → «Перенос» → «Импорт агента» (или `carry.py
import`). Прежняя `data/` на ПК остаётся рядом как `data.before-<штамп>/`.

## 6. Praxis: одно окно к ЧУЖОМУ дереву на сервере

Отдельный случай, и он живёт на сервере автора: агент ведёт СВОЙ харнесс
(Праксис), а от Hélène рядом стоит только канал — окно, телефон и мини-апп
поверх её дерева, на чтение. Ходов это окно не ведёт и ядра не несёт.

```bash
# с машины разработчика: собрать фронты, собрать пакет desk и выложить
python server/deploy_desk.py --host <адрес> --key <ключ канала>
# на сервере: поднять контейнер по рецепту, который приехал вместе с пакетом
docker compose -f /opt/praxisdesk/recipe/docker-compose.yml up -d --build
```

Что где лежит:

| Путь | Что это |
|---|---|
| `/opt/praxisdesk/` | пакет desk (`deskpkg`): канал, читалки, окно, телефон, мини-апп |
| `/opt/praxisdesk/desk.json` | манифест пакета: версия и отпечаток — их же показывает `/api/state` |
| `/opt/praxisdesk/desk.env` | ключ канала, токены ботов, имена хостов; вне репозитория и вне пакета |
| `/opt/praxisdesk/recipe/` | Dockerfile и compose контейнера канала — образ на `requirements-desk.txt` пакета |
| дерево агента | смонтировано `:ro`; на запись только `memory/.control` и `workspace/inbox` |

`desk.env` — данные установки, выкладка их не трогает:

```
PRAXIS_DESK_TOKEN=<ключ канала>
HELENE_AGENT_NAME=Праксис
HELENE_PRODUCT=Praxis
HELENE_HOSTS=<имена, по которым приходят окно и телефон>
HELENE_ORIGINS=<те же адреса со схемой>
HELENE_TG_BOT_TOKENS=<токены ботов мини-аппа>
HELENE_TG_OWNER_ID=<id владельца>
```

Имя агента и имя продукта канал отдаёт странице сам (`/config.js`,
`/m/config.js`) — руками рядом с фронтом класть нечего: такой файл уносила
первая же выкладка.

## Что здесь честно не сделано

- Один контейнер — один агент; второй агент = вторая папка и второй compose
  с другим портом; исполнитель обслуживает один контейнер (`HELENE_CONTAINER`).
- Сайт для окна (Caddy, Tailscale) команда не настраивает: имя передаётся ей, а строку в
  `Caddyfile` владелец добавляет сам (§3).
- «Да» на обновление агент со своим shell может положить сам (§3.2, шаг 3); выпуски
  не подписаны — подлинность держится на GitHub (§3.2).
- Реле ChatGPT в compose не входит.
