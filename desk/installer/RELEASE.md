# Releasing portable Hélène

The current desktop delivery is a portable archive with bundled Python. The source-only verified ZIP refresh and exact frontend/bundle recipes are in [PORTABLE-REFRESH.md](PORTABLE-REFRESH.md). Reuse the qualified runtime and unchanged native OS tools. For a Python/UI change, update the selected source, build only changed frontend assets, refresh the program inventories and package the matching platform archive. Windows uses `installer/windows_archive_entry.py` and the Python migration window; a Rust launcher/setup rebuild is not part of ordinary portable publication.

Optional large components are Whisper and XTTS only. Keep their immutable, size/SHA-pinned release asset objects and original tags available. The current voice manifests depend on `v2.3.0-rc.18`; retain that release and its large runtime/model archives when pruning other candidates. Do not retag or repoint those assets as part of the 2.3.0 desktop release. The standalone relay has its own repository and release lifecycle. Existing installed components follow their current manifests.

Use the platform snapshots in `SOURCE-SNAPSHOTS.md`. The prepared source for each platform must match its packaged `source-inputs.json`; do not infer parity from a shared version number. Preserve profiles, dirty source and Git state when checking migration or update behavior. Check only the behavior affected by a change, then perform the necessary native platform smoke checks. Healthy builds and CI jobs should be reused unless their inputs changed.

Before publication, bind the exact archives to sizes, SHA-256 values and the frozen source manifest. All internal product-version fields and component `app_version` values must describe 2.3.0; renaming an RC archive does not produce a stable build. Upload the verified artifacts to one draft, inspect uploaded identities, publish that draft and independently verify anonymous downloads. Prune obsolete candidates only after stable public-byte verification and acceptance of the owner's clean update. Keep the releases and tags referenced by component manifests, including `v2.3.0-rc.18`, and retain recoverable source/asset records before any authorized pruning.

Write factual English release notes explaining user-visible changes, startup/migration steps and material platform limits. Keep source checks, isolated runtime checks, public-byte verification and physical owner acceptance distinct.

Historical Rust shell/service and native package builders remain in the repository for their corresponding editions. They do not define the 2.3.0 portable installation path.
