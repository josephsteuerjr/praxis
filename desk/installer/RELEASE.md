# Как выпустить версию Hélène

1. **Поднять версию.** Обязательные — три `Cargo.toml`: `shell`, `setup`, `svc`.
   Они должны совпадать: сборка сверяет их и падает при расхождении, потому что
   иначе поставка была бы смесью версий. Из `shell/Cargo.toml` версию читает
   окно («О программе») и проверка обновлений.

   Ещё пять файлов объявляют версию, но продукт их не читает; сборка выписывает
   их в паспорт сборки, чтобы расхождение было видно:
   `shell/tauri.conf.json`, `setup/tauri.conf.json`, `app/package.json`,
   `mobile/package.json`, `setup/ui/package.json`.

2. **Прогнать стенды — ОДНОЙ командой.**

       python tests/run_all.py --rust

   Она сама знает состав: питон (`tests/t_*.py`), окно (`node app/test/*.mjs`)
   и Rust (`cargo test` в `shell`, `svc`, `setup`). `--list` показывает состав,
   ничего не запуская.

   ⚠ Наборов было три, и звались они тремя командами; набор окна легко забыть —
   и его забывали: `actions.test.mjs` простоял КРАСНЫМ от переделки ленты шагов
   до 09.09, проверяя слова, которых компонент давно не говорит. Помнить список
   человеку больше не нужно: **сборка выпуска зовёт этот прогон сама** и не
   собирает при красном (`build_dist.py`, шаг «стенды»; `--skip-tests` — только
   отладка).

3. **Собрать всё.** Интерфейсы: `npm --prefix app run build`,
   `npm --prefix mobile run build`, `npm --prefix miniapp run build`,
   `npm --prefix setup/ui run build`. Мини-апп — тоже: он входит в пакет desk
   (`deskpkg.py`), и без сборки пакет не соберётся.
   Затем `cargo build --release --features custom-protocol` в `shell` и `setup`,
   `cargo build --release` в `svc`.

   Реле — отдельным шагом, потому что его исходник лежит ВНЕ репозиториев
   (`_relay_prod_src/` — копия живого `/opt/relay/Code`):

       python installer/relay_src.py --check --host <адрес>   # зеркало = живой?
       python installer/relay_src.py --pull  --host <адрес>   # если разошлось
       python installer/relay_src.py --build                  # exe для Windows
       python installer/relay_src.py --build-linux            # бинарь для сервера

   `--build` кладёт рядом `RELAY-BUILD.json` с отпечатком исходника, из
   которого собран бинарь, и `build_dist` падает, если в поставку едет реле от
   другого исходника. Ровно это и случилось 09.09: в архив уехало реле от
   03.09, а починка ссылок была от 09.09.

   `--build-linux` собирает то же реле под Linux в докере (`RELAY-BUILD-LINUX.json`
   рядом) — оно едет в поставку файлом `helene-relay` и поднимается на сервере
   вместе с агентом. Бинари собираются РАЗНЫМИ командами: пересобрать один и
   забыть другой легко, поэтому сборка сверяет отпечаток каждого отдельно.

   Ядро и слой издания — тем же приёмом:

       python installer/core_src.py --check    # слой = настоящая разница?

   Раскладка объявляет: ядро в `praxis/`, издание Элен слоем в `helene/core`.
   Сборка кладёт отпечатки обоих в паспорт (`helene-build.json` → `core`) и
   говорит вслух, если объявленный слой разъехался с делом. Поставка при этом
   едет из рабочей копии — как и ехала; отказ стоит на `--from-core`, то есть
   там, где расхождение означало бы выпуск чужого дерева под нашим именем.

   Синк зеркала (ядро берётся с её прода) — по рецепту в памяти
   `praxis-public-mirror`. После КАЖДОГО синка обязательны ДВЕ сверки, и вторая
   не следует из первой:

       python installer/secret_scan.py <дерево> <живые секреты.json>
       python installer/personal_scan.py <репозиторий> <ревизия ДО синка>

   ⚠ 10.09 первая прошла честно — ни одного живого секрета в зеркале, — а в
   публичный репозиторий уехал Telegram-id постороннего человека: он не в `.env`,
   он в фикстуре теста и выглядит как обычное число. Пришлось переписывать
   историю и переносить тег. Вторая сверка ловит именно этот класс и читает весь
   индекс git, а не одну папку.

   Тело руки `computer` — из дерева, но в чужой target-каталог, чтобы `live/`
   оставалось чистым: в `live/body` —
   `cargo build --release -p praxis-body -p praxis-bridge --target-dir ../../_body_target`
   (сборка ищет `_body_target/release/praxis-body.exe` и `praxis-bridge.exe`
   рядом с репозиториями и кладёт их как `helene-body.exe` и `helene-bridge.exe`).
   Затем `python installer/build_dist.py` — **без `--skip-runtime`**.

   `--skip-runtime` и `--allow-partial` — только для отладки. Выпуск собирается
   с полным рантаймом: зависимости не запиннены, и рантайм меняется сам от
   того, что выложил PyPI, — «рантайм не менялся» проверить нечем.

   Итог — `installer/build/Helene-<версия>.zip` и рядом
   `Helene-<версия>.zip.sha256`; с 1.1.0 — ещё `Helene-<версия>-setup.exe`
   (установщик NSIS из `installer/windows/helene-setup.nsi`: распаковывает
   поставку и открывает мастер; makensis берётся из PATH или из NSIS Tauri в
   `%LocalAppData%\tauri\NSIS`) и его `.sha256`. Для людей в выпуске — setup.exe,
   архив — для кнопки обновления в окне (она берёт из выпуска только .zip).

4. **Что сборка проверяет сама** (падает, а не предупреждает): версии трёх
   `Cargo.toml` совпадают; дерево агента на месте и непустое; скачанное
   (embeddable CPython, get-pip, busybox, MinGit) совпадает с записанными в
   `build_dist.py` контрольными суммами — включая то, что лежит в кэше; все
   шесть exe собраны (оболочка, установщик, служба, реле, мост и тело);
   телефон собран; рантайм импортирует свои зависимости;
   версия ВНУТРИ `helene.exe` и `helene-setup.exe` совпадает с объявленной в
   их `Cargo.toml` (подняли версию, но не пересобрали — сборка падает);
   ни в одном едущем файле нет ничего похожего на кред (сканируется
   содержимое, кред-полом самого дерева агента, плюс форма присвоения
   `PASS=…`; при полной сборке — ещё и текстовые файлы рантайма);
   пакет desk собирается целиком (`deskpkg`), то есть все его части на месте —
   канал, читалки, окно, телефон, раннер и ресурсы; реле собрано из того же
   исходника, что лежит в зеркале (`RELAY-BUILD.json` против отпечатка). Прошла
   сборка — прошло перечисленное здесь, и только оно; «состав архива
   проверен» это не значит.

   Чего сборка НЕ проверяет и о чём стоит помнить: `helene-svc.exe` собирается
   голым cargo и версии внутри не несёт вовсе — про него сборка честно пишет
   «версии внутри нет — сверить нечем», так что служба остаётся на совести
   шага 3 (сборки). И конституция: `resources/SOUL.md` вшивается в бандл установщика на
   этапе `npm --prefix setup/ui run build` — правка конституции без пересборки
   этого бандла уедет в поставку старой.

   Глазами остаётся посмотреть `helene-build.json` в корне архива: версия,
   время сборки, git-хэши обоих репозиториев, `"complete": true`, суммы
   скачанного и список пакетов рантайма. Хэш с суффиксом `-dirty` и
   `"dirty": true` означают, что сборка сделана из несохранённых правок: по
   такому паспорту релиз не воспроизводится, коммить надо до сборки.

   Свои буквальные секреты (пароль сервера, адреса) можно положить построчно в
   `installer/secret-strings.txt` — сборка проверит, что их нет в поставке.
   ⚠ Файл ЗАВЕДЁН 11.09 (пароль VPS, его адрес, прежний пароль) и лежит в
   `.gitignore`. Сборка печатает «страховка secret-strings.txt: N строк»; если
   она печатает «НЕ ПОДКЛЮЧЕНА» — файла нет, и половина гарда не работает.
   Дописывать туда стоит всё, что есть у владельца буквально: почта, домены,
   токены ботов, ключи провайдеров.
   Файл в `.gitignore` и в репозиторий не попадёт. Пока файла нет, сборка
   печатает «страховка НЕ ПОДКЛЮЧЕНА»: это не отказ, но и не «чисто».

5. **Выложить.** Записать изменения в `CHANGELOG.md`. На GitHub: тег
   `v<версия>`, релиз с этим тегом, к релизу прикрепить
   `Helene-<версия>-setup.exe` (с суммой) и `Helene-<версия>.zip`. В описании релиза первая строка — что изменилось:
   её показывает окно. Второй строкой — sha256 из
   `Helene-<версия>.zip.sha256`: релиз не подписан, и это единственное, чем
   скачавший может проверить, что получил именно этот файл.

6. **Обновление у пользователя.** Адрес проверки уже записан в `helene.json`
   поставки: `https://api.github.com/repos/josephsteuerjr/praxis/releases/latest`.
   Окно сравнивает `tag_name` со своей версией, показывает первую строку
   описания и берёт sha256 — из digest ассета GitHub, а без него из второй
   строки заметок релиза (поэтому она обязательна). «Скачать и установить»
   (`update_download` → `update_install` в оболочке): архив в «Загрузки»,
   сверка суммы (не сошлась — файл удаляется, отказ словами), распаковка
   рядом, запуск `helene-setup.exe`; дальше — установщик.

   **Что происходит при установке поверх** (`setup/src/install.rs`): новый
   `helene.json` не пишется с нуля, а сливается с существующим — визард владеет
   только своими ключами (`merge_config`; блок `model` — по полям, `keys` и
   `compact_model` окна переживают), остальное — телефон, песочницу,
   MTProto, адрес обновлений — сохраняет. `data/soul/SOUL.md` пишется, ТОЛЬКО
   если файла ещё нет: выросшую конституцию установка не трогает, и это видно в
   расписке («конституция оставлена как есть»). Память, дневник и комнаты в
   `data/` не трогаются вовсе.

   **Статика окна и рантайм.** Сборка кладёт в `app/static/.helene-static.json`
   манифест (sha256 файлов + общий `digest`, он же в `helene-build.json` →
   `static`). Установщик сравнивает манифест новой поставки с манифестом той,
   что стоит: равны — `app/static` пользователя не трогается вовсе; разные —
   заменяется, прежняя папка отложена в `app/static.prev`, в `helene.json`
   ставится `installed.static_prev` (окно говорит об этом словами); нет
   манифеста в установке (до 0.4.0) — заменяется. `runtime/` копируется,
   только если в `helene-build.json` разошлись `python`, `downloads` или
   `packages`. Правило целиком — `resources/ОБНОВЛЕНИЕ.md`; стенды —
   `static_follows_the_release_not_the_user`,
   `runtime_is_skipped_only_when_the_passport_matches` (`cargo test` в setup).

   Пошаговая инструкция для пользователя — `resources/ОБНОВЛЕНИЕ.md`, она едет
   в корень поставки. Если правишь поведение установки поверх — правь и её.

## Сборка для macOS (Apple Silicon)

С 0.7.1 тот же выпуск несёт второй архив — `Helene-<версия>-macos-arm64.zip`,
рядом `Helene-<версия>-macos-arm64.zip.sha256` и `install.sh`. Windows-архив
при этом не трогается. Собирается не на машине владельца, а на раннере GitHub
`macos-15` (Apple Silicon) — `.github/workflows/macos.yml` → `desk/installer/build_mac.py`.

**Порядок выпуска 0.8.0** (план 19.09, §4) — по шагам, потому что два из них
переставить нельзя:

1. Влить ветку в `main` — иначе кнопки `workflow_dispatch` у workflow не будет
   (GitHub показывает её только с ветки по умолчанию).
2. Windows: `python installer/build_dist.py --skip-runtime` и он же
   `--variant praxis` → `Helene-0.8.0.zip` и `Praxis-0.8.0.zip` (с 1.1.0 рядом с каждым —
   `<Продукт>-<версия>-setup.exe` из `installer/windows/*.nsi`).
3. `gh release create v0.8.0` — в выпуск сразу кладутся Windows-архив,
   Praxis-архив и **`install.sh` ПРЕЖНЕЙ версии**.
4. `gh workflow run macos.yml -f tag=v0.8.0 -f upload=true` — раннер соберёт
   Mac-архив (дерево возьмёт из Windows-архива этого же выпуска) и выложит его,
   заменив `install.sh` своим, свежим (`--clobber`).

⚠ **Почему `install.sh` прежней версии кладётся сразу.** Однострочник установки
ведёт на `releases/latest/download/install.sh`, а «latest» — это новый выпуск с
той секунды, как он создан. Пока идёт Mac-сборка (≈20 минут), этого файла в нём
нет, и каждый, кто в эти минуты ставит Hélène, получает 404. Скрипт прежней
версии в это окно работает (он тянет свой тег), а раннер потом заменит его на
новый `--clobber`-ом.

1. **Windows-выпуск уже выложен.** Mac-сборка берёт дерево агента (`tree/`) и
   `server/` из `Helene-<версия>.zip` этого выпуска байт в байт — под одним
   тегом не должно быть двух разных деревьев. Пакет desk (`app/`) собирается
   заново из ветки: движок на Mac другой. Версия ветки обязана совпадать с
   тегом, иначе сборка падает.

2. **Выкладывать — ТОЛЬКО кнопкой и только после влития в `main`.**
   `workflow_dispatch` GitHub показывает лишь с ветки по умолчанию: пока файла
   workflow нет в `main`, кнопки нет вовсе, а `gh workflow run ... --ref <ветка>`
   до влития невозможен.

       gh workflow run macos.yml -f tag=v0.8.0 -f upload=true
       gh run watch

   Шаг выкладки стоит на гарде `[ "$TREE_TAG" = "$TAG" ]` — выложить можно
   только сборку, чьё дерево агента взято из ТОГО ЖЕ выпуска, которым назван
   архив. `--clobber`: повторный прогон заменяет прежнюю Mac-сборку,
   Windows-архив не трогается.

   ⚠⚠ **Артефакт push-прогона в выпуск НЕ кладётся.** Прогон от push в
   `port/macos`/`port/macos-body` — проверочный: входы (`inputs.upload`) там
   пусты, а дерево агента берётся из ПОСЛЕДНЕГО существующего выпуска
   (`TREE_TAG`, умолчание — прошлый выпуск, с 25.09 не ниже v0.8.5: в более старых архивах
   `tree/body` без darwin-веток не собирается на Mac) — выпуска новой версии ещё нет. Внутри такого
   архива дерево прошлой версии, а имя файла обещает новую. Поэтому артефакт
   такого прогона и называется не по-выпускному:
   `Helene-<TAG>-macos-arm64-tree-<TREE_TAG>` (шаг «Имя артефакта»). Смотреть
   его глазами можно, выкладывать — нет:

       gh run list --workflow macos.yml            # id прогона
       gh run download <id> -n Helene-v0.8.0-macos-arm64-tree-v0.7.2

   Проверка у любого архива в руках, одной строкой: `helene-build.json` →
   `source_release.tag` обязан совпадать с `version`. Разошлись — это
   проверочная сборка, а не выпуск.

3. **Что сборка проверяет сама** (падает, а не предупреждает): версия ветки =
   тег; скачанное (python-build-standalone 3.14.7, исходник git 2.55.0)
   совпадает с суммами в `build_mac.py`, а Windows-архив — с суммой актива на
   GitHub; число файлов дерева сходится с паспортом того архива; рантайм
   импортирует `SMOKE_IMPORTS` и стенды питона и окна (`tests/run_all.py`)
   зелёные ИМЕННО на этом рантайме; колёса не требуют macOS новее объявленного
   `LSMinimumSystemVersion` (14.0 — столько просят колёса голоса); все пакеты
   встали колёсами, кроме `pyaes` (чистый Python исходником); `runtime/git`
   отвечает на `--version`, `--exec-path` внутри себя и делает `git init`;
   реле стоит на коммите `build_mac.RELAY_COMMIT` (сейчас `f8ef18f`, 0.8.2); тело
   (`helene-body`, `helene-bridge`) собрано из `tree/body` архива выпуска —
   одни крейты на обе системы (`--target-dir` в кэше сборки), оба
   бинаря отвечают на `--help`, их лицензии — `licenses/body/`; оба бандла,
   реле, мост, тело и всё Mach-O в рантайме подписаны ad-hoc и проходят
   `codesign --verify`; состав архива полный (`REQUIRED_ROOT`); секрет-гард
   тот же, что у Windows (кред-пол дерева + форма присвоения + текстовые файлы
   рантайма). Дальше workflow гоняет `cargo test` в `shell` и `setup` и
   `cargo test -p praxis-body -p praxis-bridge` (стенды тела на настоящем Mac),
   живые проверки ограды (`tests/t_fence_macos.py`), ставит программу тихо в
   `~/Applications/Helene` с `"computer": true`, открывает `Helene.app`,
   снимает экран, дёргает `/api/health` и `/api/state` канала по секрету
   дерева и ждёт до 40 с `connected: true` в `data/memory/.state/body.json`
   (иначе хвосты `data/body/*.log` и падение); потом живые стенды тела
   бинарями сборки — `tests/t_body.py` и `tests/t_body_macos.py` (контракт
   тела: status с `platform`/`tcc`/`hints`, снимок ok+PNG или честный отказ,
   окна, процессы, буфер обмена, дерево окна Helene). Разрешения TCC у
   раннера — какие есть: без них стенд печатает отказ словами и не падает;
   падает на лжи (снимок «ok» без разрешения) и на поломке.

   С 0.8.0 прогон гоняет и ОБНОВЛЕНИЕ поверх установленного: тем же
   `install.sh --from <архив>`, тихим путём (мастер снимает демон, копирует,
   ставит демон заново), и дальше сверяет, что `helene.json` цел
   (`computer.enabled`, `installed.service`), `data/` цела (ключ канала
   `data/memory/.state/desk-token` тот же байт в байт), паспорт в корне — от
   свежей поставки, служба снова загружена и канал отвечает без окна.

   Чего сборка НЕ проверяет: мастер и окно живьём в руках человека — снимок
   экрана из артефактов посмотреть глазами; ДИАЛОГ ПАРОЛЯ — ни у брокера, ни у
   службы, ни при обновлении со службой (на раннере `GITHUB_ACTIONS=true` и
   sudo без пароля, поэтому административные шаги проходят молча, а у человека
   это два диалога подряд); фоновое обновление из окна (оно запускает
   `install.sh` отсоединённо — покажет ли macOS диалог такому процессу, никто
   не видел); выдачу разрешений TCC руками — чек-лист для человека с Маком в
   `ПЕРВЫЙ-ЗАПУСК.md` архива.

4. **Глазами** — `helene-build.json` из артефактов: `platform: macos`,
   `arch: arm64`, `complete: true`, `git.desk` без `-dirty`, `source_release`
   (тег, актив и его sha256, паспорт Windows-архива коротко), `python` 3.14.7,
   `git_bundle`, `macos_min` и `macos_floor_wheels` рядом (второе не больше
   первого), `relay.commit`, `body.source` (`tree/body`) и `body.commit` (коммит дерева
   поставки; при откате на зеркало — `praxis/body` и голова `CORE-SOURCE.json`) с
   `body.digest` и `body.exe_sha256`, `signed_adhoc`,
   `packages`.

5. **В описании выпуска** — третьей строкой сумма Mac-архива, тем же видом,
   что и Windows: `sha256 Helene-<версия>-macos-arm64.zip: <digest>`. Окно на
   Mac берёт сумму из digest актива GitHub или из этой строки. Однострочник
   для документов — без номера версии, GitHub отдаёт последний выпуск:
   `curl -fsSL https://github.com/josephsteuerjr/praxis/releases/latest/download/install.sh | sh`
   (какой тег качать, знает сам `install.sh`: `HELENE_TAG_DEFAULT` штампует сборка).

6. **На самом Mac** то же руками: `python3 installer/build_mac.py --from-release v0.8.0`
   (нужны Rust, Node 24, Xcode Command Line Tools, `gh` с входом). Итог — в
   `installer/build-mac/`. `--skip-runtime`, `--skip-rust`, `--skip-tests`,
   `--allow-partial`, `--skip-body` (полусборка без тела: паспорт получит
   `complete: false`) — только отладка, как у Windows-сборки. Чистые части
   сборки (плист, имена активов, паспорт, отбор архива, Mach-O, штамп
   `install.sh`, отпечаток и паспорт тела, лицензии, статика workflow) держит
   `tests/t_build_mac.py` на любой ОС.

7. **Про разрешения тела.** Подпись ad-hoc новая на каждую сборку, а TCC
   помнит программу по подписи: после КАЖДОГО обновления у пользователя слетают
   «Запись экрана» и «Универсальный доступ» — об этом говорят `ПЕРВЫЙ-ЗАПУСК.md`
   и `ОБНОВЛЕНИЕ.md` (убрать `Helene` из списка и добавить снова). Уйдёт только
   с Developer ID, которого по решению владельца нет.

## Открытые остатки цепочки поставки

Названы, чтобы их не считали решёнными.

- **Подписи кода нет.** SmartScreen при первом запуске просит «Подробнее →
  Выполнить в любом случае», об этом сказано в ПЕРВЫЙ-ЗАПУСК.md.
- **Контрольные суммы скачиваемого сняты с рабочих файлов, а не с подписи
  издателя** (`SHA256` в `build_dist.py`, дата в комментарии). Они защищают от
  подмены и порчи ПОСЛЕ этой даты — не доказывают, что в тот день всё было
  чисто. Меняешь `PY_VERSION` — снимай суммы заново, сверяя с python.org.
- **pip ставит без `--require-hashes`.** Версии установленного пишутся в
  `helene-build.json` (`packages`), то есть сборку можно опознать и повторить,
  но подмену пакета на PyPI это не ловит.
- **Windows-артефакт собирается на машине владельца**, на той же, где живёт
  агент с рукой shell; CI у него нет. Mac-артефакт — на раннере GitHub
  (`macos.yml`), но подписан ad-hoc: Developer ID и нотаризации нет, отсюда
  установка через `curl`, а не через образ, и слетающие после каждого
  обновления разрешения тела (TCC помнит подпись).
- **Исходник тела — один** (с 25.09): Windows-сборка берёт крейты из `live/body`
  соседа, Mac-сборка — из `tree/body` того же архива; darwin-ветки живут в дереве
  издания и в слое `helene/core/body`, зеркало `praxis/body` их не несёт (её прод —
  Windows-тело). Windows-тело теперь с происхождением: `installer/body_src.py --build`
  пишет `_body_target/BODY-BUILT.json`, `build_dist.py` отказывает, если exe собраны не
  из живого исходника (как у реле).
