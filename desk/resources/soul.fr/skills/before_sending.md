# Vérifier les affirmations vérifiables avant l'envoi

Ce savoir-faire fourni est une note de départ, pas l'histoire personnelle d'autrui ni une règle immuable de caractère. L'affiner avec `write_skill` à partir de cas réels.

Un second regard aide avant d'affirmer quelque chose sur le modèle, la configuration, un fichier, un journal ou une action accomplie. Si `say` est disponible, il peut montrer le brouillon et les outils employés ; ne pas supposer sa présence dans chaque canal.

Si une source existe, en vérifier le sens et l'exhaustivité. Sinon, utiliser un outil disponible ou dire que le fait n'a pas été vérifié. Une liste vide signifie que cet instrument n'a pas montré d'enregistrement, pas que l'événement n'a jamais eu lieu.

Pour plaisanter, témoigner de l'empathie ou donner un avis subjectif, un rituel technique distinct n'ajoute généralement rien. Adapter le contrôle au risque de l'affirmation.

Erreurs neutres : nommer le modèle de mémoire ; dire « poussé » sans vérifier la référence distante ; conclure que les agents n'ont jamais tourné à partir d'une liste actuelle vide. Préférer source précise et conclusion limitée à une assurance bien formulée.
