# 从好用工具到完整工作

新增工具、改变流程或总在猜下一步时阅读。
工具说明解释如何调用，技能解释如何用它获得经过验证的结果。

说明包含参数、限制、副作用和响应含义；技能帮助选择路径与分支。
强制检查、秘密保护、版本与锁仍在代码中，文字不能替代，也不能产生权限。

## 从完整情境开始

选择重复发生的完整任务，例如安排续办、检查连接或迁移项目。
不为每个按钮单写技能。已有合适流程时，补充分支，保留单一事实来源。

写明触发条件、目标结果及何时换路径。只使用现有工具与可用数据，
提到计划中的功能，不会让它自动可用。

工具名和签名要对照完整模式，调用前不需要另做展开。
脚本可通过 `h.describe` 读取模式。工具未提供时，检查 `my_capabilities`，
不能编造名字或参数。实际状态和模式比旧技能更可靠。

## 让下一步明确

1. 行动前需要哪些事实，到哪里获取。不重复仍然有效的检查。
2. 做什么，依据什么观察选择分支。名字、接收者、实例与权限必须对应当前工作。
3. 怎样确认结果：回执、新状态或实际行为。“已接受”不总是“已完成”。
4. 完成后留下什么：结果、保存位置及未完成步骤。

## 拒绝、部分完成和未知结果

修改前遭拒绝，先解决原因，再重复所需步骤。
缺少权限时，技能不能补发权限，应明确指出缺少的能力。

部分完成时，保留成功回执，继续剩余部分。重跑整批可能产生重复效果。
超时后先按操作标识或地址检查实际状态，没回复不等于没效果。
无法确定结果，就记录不确定，不能写成成功或拒绝。
只在确实能回退时说明回退方式。

## 简短路径

修改文件：读取内容与版本 → 用预期版本调用 `edit` → 检查回执和新内容。
出现 `in_doubt` 时先重读状态和日志，盲目重写可能覆盖已成功的修改。
具体参数以模式为准，不从这个例子猜。

工程任务先读 [coding_hands](coding_hands.md)，绑定真实目录，研究、修改，
验证行为和 diff，再带证据结束。单次成功调用不能代替完整路径。
技能不授权超出当前任务和权限修改自身代码。

简单读取不需要独立的多步骤技能。新流程至少有简短示例及适用边界。
项目示例应标为项目示例，不能冒充已验证的产品功能。

## 检查技能本身

走过正常请求、拒绝、部分结果和发送后断线的情况。
每次观察后都应有清楚的下一步。需要猜时就补充分支；
只重复模式时，就缩短参考内容，说明决策。
不能用堆积一般禁令代替修复不好用的工具。
