# 修改自己的代码

阅读自己的代码是日常工作。在授权任务范围内可以修改，但必须知道
修改哪个代码树，以及如何应用和撤销结果。

## 先找到真实的代码树

数据、源代码和程序可能分开存放。`data/` 中有仓库，不代表其中包含
`tree/`。检查实际路径、`git status`、分支和受版本管理的文件。
“灵魂”目录的快照不是代码快照。

`coding_session` 使用 `target="self"` 时，目标是配置中的根目录，
不保证就是想修改的模块。检查返回的 `source_root`、`root`、
`isolation` 和 `proposal_id`。目标不对时，提供已核实的绝对路径。
`isolation="auto"` 可能创建提案或 Git worktree；无法隔离时，
也可能说明原因后转为直接操作。`isolation="direct"` 会修改源目录。
不能只是为了绕过拒绝就选择它。第一次写入前，确认实际操作范围。

## 真正可用的回退路径

Forge 保存任务、结果和工作副本，但这不是所有受影响目录的备份。
产品更新会使用源代码快照并迁移本地修改，但不能撤销我的任意改动。
先核实哪些提交和原始文件确实可用。缺少所需原件时，先保存到允许的
位置再修改。不覆盖他人尚未提交的工作。

重要数据备份未必包含代码。导入错误可能阻止下次启动，进程监督器
不会自动修好它。应用前，需要验证过的回退办法，以及留给所有者的记录。

## 工作步骤

1. 阅读模块、调用方和当前约定。旁边的文档可能描述另一套安装环境。
2. 在任务范围内使用 `coding_inspect` 或 `code_query` 查找符号、引用
   和依赖。检查模式以及结果是否完整。
3. 记录目标、成功标准、授权、验证与回退方式。在范围内沿用已有授权。
4. 创建任务，核实实际根目录和隔离方式。
5. 保存原始状态，通过 `edit` 进行小而连贯的修改。
6. 通过 `coding_run` 检查语法、导入及相关行为。
   `python -m py_compile` 不能代替导入或实际场景验证。
7. 检查最终 diff，按正式方式应用。需要 `restart_self` 时说明原因，
   随后检查就绪状态、原始场景和历史是否保留。
8. 记录改了什么、如何验证、原件在哪里、怎样回退。

工作进程的结果未知时，不删除锁，也不手工宣布完成。
核实进程所有权，使用正式恢复流程，并保留工作副本与历史。
单纯重启应用不能证明这些事实。

## 不同的修改对象

Python 源代码、构建后的网页界面、运行框架、服务、中继和启动器
有不同的构建及应用方式。修改构建产物不等于修改源代码，更新时可能
丢失。分别核实每个目录的权限，不能换个工具绕过权限。
参见 [code-map](code-map.md) 和 [fence-and-broker](fence-and-broker.md)。

子智能体和重复的模型审查会按所有者的套餐消耗限额或费用。
小修改不组建多余团队。他人的审查要注明归属，重要证据仍需亲自打开查看。
