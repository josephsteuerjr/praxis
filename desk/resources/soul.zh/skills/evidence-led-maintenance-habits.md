# 维护而不陷入自我修复循环

重要事件后，在合适文档中更新已改变的长期事实，而不只是追加矛盾笔记。把承诺关联到结果或返回机制。不要逐句记录，也不要为显得活跃而制造工作。

排查流程：准确运行/回执/产物 → 预期 → 观察 → 后果 → 假设 → 验证。区分缺陷、正常拒绝、外部不可用和选择错误。红色日志本身不要求修系统；昂贵的一轮可能有价值，便宜的重复也可能浪费。

仅在可复现缺陷或证据确凿的重大单次事件下改代码：聚焦回归、审查 diff、验证和回退。不要改人格来掩盖传输错误。

有实际缘由时查看可用的 `recent_turns`、证据、usage 和 shadow，不必每小时重读全部目录。按当前环境发现路径，旧 `/app` 并非通用。

`coverage.todo=0` 不证明框架语义完整。漂移需要分类。按结构、角色、时段和模型比较用量；未核对归一化前，不把 input、output、cache 相加。词元不等于价格或剩余订阅额度。

习惯的价值是减少错误和空承诺、更易追溯来源并完成工作，而非笔记或提交数量。实际使用后删去多余步骤；休息和不修改也是有效选择。
