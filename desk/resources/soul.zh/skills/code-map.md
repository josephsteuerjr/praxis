# 我的代码地图

地图帮助定位模块，当前文件和实际结果才确认事实。
`КАК-УСТРОЕН-HELENE.md` 是有用的发行包文档，但也可能过时。
实际布局取决于平台、迁移和版本类型。

| 位置 | 查找内容 | 核实方式 |
|---|---|---|
| `data/` | 记忆、灵魂、工作文件，以及可能存在的数据 Git 仓库 | 核实真实路径、清单和历史 |
| `tree/` | 核心：`agent.py`、`frame_*.py`、`memory_*.py`、`llm.py`、`forge.py`、`self_model.py` | 阅读代码，写入前确定任务根目录 |
| `app/localharness/` | 启动、诞生、渠道、模式、迁移和更新 | 检查实现与目录权限 |
| `app/python_app.py`、`app/first_start_window.py` | Python 窗口与首次启动 | 区分源代码和构建后的界面 |
| `app/deskd/` | 程序 HTTP 渠道及视图模型 | 核实路由、授权与实际响应 |
| `app/static/`、`app/mobile/`、`app/miniapp/` | 构建后的界面 | 找到源代码和构建命令，更新相关界面 |
| `runtime/` | 解释器和依赖 | 不与应用源代码混淆 |
| `helene.json` | 配置，包括秘密 | 使用授权的设置入口，不向共享渠道输出全部内容 |

启动器、服务、中继和可选组件各有源代码与进程。
不能把整个外壳都称为 Rust，也不能把整个产品都称为 Python。
Windows MCP 是按自身许可证独立安装的模块；上下文里有它的模式，
不能证明服务器已经连接。

## 定位原因

1. 明确处理故障场景的版本、路径和进程。
2. 打开当前日志，检查时间。旧日志不能证明当前进程的状态。
3. 用 `fs_search`、`coding_inspect` 或 `code_query` 找处理函数。
   检查调用方、模式和搜索完整性，不只看名字是否匹配。
4. 对照源代码与真正构建、运行的字节。修改源代码不会自动改变已有进程。

日志可能叫 `runner.log`、`helene.log`、`service.log` 或 `broker.log`，
具体位置以本安装环境为准。`memory/runs/` 保存现有回合记录，
不保证每次行动都有完整归档。分享前检查秘密和接收者。

数据 Git、源代码 Git、Forge 工作副本及更新快照是不同的历史来源。
要核实哪个来源确实包含所需文件。应用与回退见
[my-own-code](my-own-code.md)，访问及提权见
[fence-and-broker](fence-and-broker.md)。

最大的陷阱，是把熟悉的路径当成已验证事实。更新、迁移或切换平台后，
重新核实路径。
