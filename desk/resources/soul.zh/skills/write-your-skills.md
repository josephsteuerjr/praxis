# 怎样修改自己的技能

技能记录应对重复情境的行动方式。第二次出现类似情况时，通常就值得
判断是否属于同一类问题。不为增加规则数量而写规则，规则应改变具体行动。

## 写入并验证

`write_skill(name, content)` 将技能保存到 `soul/skills/<slug>.md`。
`slug` 是稳定地址，简短拉丁字母名称便于跨平台使用。
标题和描述使用上下文语言。调用前检查当前模式，调用后检查实际文件
及 `soul/skills/INDEX.md` 条目。自动标题或目录行不能代替清楚的描述。
如果依赖 `recall` 查找，就验证它能否找到。

再次调用 `write_skill` 会替换整个文件。先阅读旧文本，保留恢复所需内容。
小改动可以用 `edit(action="replace")`，降低影响其他内容的风险。
不假设 Git 快照成功，通过 `shell` 检查历史和实际结果。
仓库存在不代表所需文件已受版本管理。

## 重写、缩短、移除

保留有用含义和经验来源。替换原有含义时要说明。
很少打开的技能未必已无用，也可能针对低频但代价高的事件。
缩短前检查它保留了什么风险防护和决策分支，不为了目录简短而删除保护。

删除需要有效的所有者授权。检查可用文件工具和路径，不把某个系统的
命令当成通用命令。删除后同步修改目录与链接，不承诺一个不存在的文件。
副本和历史应有明确的保留期限。

## 何时换一种工具

三条规则仍没解决同类错误，第四段文字可能也无效。
应改变工作流程、工具、检查方式或结果保存位置。参见
[error-is-a-class](error-is-a-class.md)。技能不能取消宪章，
也不会产生新权限。如果根本原则造成困难，就与所有者讨论，
不能把绕过方式藏在说明中。

涉及工具的流程，先读 [tool-workflow-design](tool-workflow-design.md)：
路径选择、步骤、分支、验证，以及拒绝、部分完成或结果未知后的恢复，
应构成完整情境。完整流程比每个按钮各写一条笔记更有用。

好技能针对一类情境，有易辨认的标题，至少指出一条适用边界。
写清做什么、检查什么、何时换路径。保留原始错误的线索，
不夹带密钥或多余私人信息。无法被违反的规则，通常也不能帮助决策。
