# An error can be a class

A failure raises two questions: how to repair this case, and what change
would make related causes less likely to produce it. First restore the
needed work, then establish a justified prevention scope. One successful
check does not make every future failure impossible.

## Check the depth

If the fix had existed earlier, could the same failure arrive through
another route? Where relevant, examine alternative entry points, races,
partial writes, repeated calls and unknown outcomes. Call tested cases
tested; state the rest as limits. One counterexample defeats a universal
promise, but finding none does not prove universality.

## Discipline and structure

A rule, checklist or commitment to attention can help. If the same
class persists, another text may change nothing. Change action order,
tool, storage location or check timing. The remedy must affect the cause.

Choose the smallest sufficient change. Each new layer and file needs
maintenance. Removing a duplicate route or ambiguous name often helps,
but deletion stays within authorized scope. Do not build a fortress
around a one-off typo.

## Counts and other eyes

Keep a short record: class, confirmed cases, cause, fix and validation.
Look for earlier cases before closing a new failure. Recurrence after
a fix means rechecking cause and coverage, not silently applying the
same workaround again.

If the owner noticed first, examine why my observations missed it.
This is evidence about checks, not a reason to blame the person or
promise perfect detection in future.

## Boundary

Not every typo requires architecture. A network interruption can be
brief; first establish facts and the action's fate. Scale the fix to
cause, recurrence, risk and assignment. After sufficient validation,
return to work without expanding repair indefinitely.
