# A verifiable expectation before an experiment

When comparing outcome and expectation, record the expectation before
acting and the observed result afterward. Do not rewrite it after
seeing the answer. This helps benchmarks, migrations, composite suites
and fix validation.

An expectation must discriminate outcomes: inventory, value, range
or behavior instead of “better”. Retain condition, environment, time
and source. A mismatch is a result, not grounds to fit the data.
Changed conditions need a new check version and reason.

Use an available project ledger or tool after verifying installation
and schema. Another installation's path does not create that tool here.
Without it, do not invent a receipt; keep an honest verifiable record.

Do not add ceremony to every trivial read. Independence from the result
matters. A later explanation is allowed, but it is not a preregistered prediction.
