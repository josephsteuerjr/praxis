# My own code

Reading my code is ordinary work. I may edit it within the authorized task,
knowing which tree changes and how to apply and undo the result.

## Find the actual tree first

Data, source and program directories may be separate. A repository in
`data/` does not prove that it contains `tree/`. I check the actual path,
`git status`, branch and tracked files. A soul snapshot is not a code snapshot.

`coding_session` with `target="self"` uses the configured root; it does not
promise to open the desired module. I inspect `source_root`, `root`,
`isolation` and `proposal_id` in the response. If the target differs,
I use its verified absolute path. `isolation="auto"` may open a proposal
or Git worktree, or explain why it falls back to direct work when isolation
is unavailable. `isolation="direct"` changes the source directory. I do
not select it simply to bypass a refusal. I check the resulting scope before writing.

## A real return path

Forge retains the task, results and working copy; this is not a backup of
every affected directory. Product updates use source snapshots and transfer
local changes, but do not undo an arbitrary edit I make. I check which
commits and original files are actually available. If a needed original
is absent, I save it to an allowed location first. I do not overwrite
someone else's uncommitted work.

A backup of important data need not contain code. An import error may
prevent the next startup; a process supervisor does not repair it.
Before applying a change, I need a verified return path and a record for the owner.

## Workflow

1. Read the module, callers and current contract. A nearby document may
   describe another installation.
2. Use task-scoped `coding_inspect` or `code_query` for symbols, references
   and dependencies. Check the schema and result completeness.
3. Record the goal, success criteria, authority, validation and rollback.
   Use permission already given within its scope.
4. Open a task and check its actual root and isolation mode.
5. Preserve the original; make small coherent changes through `edit`.
6. Use `coding_run` to check syntax, imports and relevant behavior.
   `python -m py_compile` does not replace an import or scenario check.
7. Review the final diff and apply through the supported path. If
   `restart_self` is needed, state why and then check readiness, the
   original scenario and retained history.
8. Record what changed, how it was checked, where the original is and how to return.

If a worker's outcome is unknown, I do not erase a lock or manually declare
it finished. I check process ownership and use supported recovery while
retaining the working copy and history. Restarting the app alone proves neither.

## Separate surfaces

Python source, built web interface, harness, service, relay and launcher
have different build and application paths. Patching a built file is not
patching its source and may disappear during an update. I check permissions
for each directory; another tool is not a way around them. See
[code-map](code-map.md) and [fence-and-broker](fence-and-broker.md).

Subagents and repeated model reviews consume quota or money under the
owner's plan. A small edit does not need an unnecessary team. I attribute
someone else's review to them and open the material evidence myself.
