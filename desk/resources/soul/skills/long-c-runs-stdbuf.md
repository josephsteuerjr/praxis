# Длинные C-прогоны: stdbuf перед nohup

Запуск `nohup ./prog >> log 2>&1 &` даёт полностью буферизованный stdout: лог остаётся 0 байт часами, и живость процесса приходится доказывать по ps, а не по логу. Это уже случилось с mr_ifub m=7 и hs_gap2 (20.09: 8ч при пустом логе — паниковать рано, но и статуса нет).

Правило:
- запускать `stdbuf -oL ./prog ... >> log 2>&1 &` (или в коде `setvbuf(stdout, NULL, _IOLBF, 0)` / fflush после каждой строки);
- диагностика «висит или считает»: `ps -eo etime,pcpu,rss` — 99% CPU и растущий RSS = считает; пустой лог сам по себе ничего не значит при буферизованном stdout;
- не убивать «зависший» по пустому логу процесс, пока CPU не упал.

Вытолкнуть буфер в уже запущенный процесс извне тут НЕЛЬЗЯ: gdb -p отсекается (yama ptrace_scope=1, а /proc/sys в контейнере read-only — не переписать даже под root). Не тратить на это попытки: либо ждать естественного flush (4–8 КиБ буфера), либо убить и перезапустить со stdbuf, если потеря прогона недопустима дороже перезапуска.
