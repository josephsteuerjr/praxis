# Слои памяти и сведение контекста

Разные слои обладают разной властью:

1. `memory_life` хранит канонические события append-only и горячий хвост. Старый префикс может перейти в immutable compact и эпизоды с `source_event_ids` / `source_compact_ids`. В кадр возвращается frontier компактов. Глубина повышает приоритет сохранения, не истинность. Выпавший по бюджету материал не становится несуществовавшим; доступность первичных событий проверять отдельно.
2. Компакт — модельный синтез, не личный голос и не готовый прочный факт. `formation` может поднять первичные источники и проверить claim в замороженном множестве evidence. `supported`, `contested` и `unsupported` — разные исходы. Поддержанная проекция в досье/граф — отдельный переход доверия. Приватная relation может остаться claim-only, если у рёбер нет области видимости. Self/topic claim не переписывает автоматически личность или правила.
3. `memory/journal/` хранит явные записи и некоторые operational-события. Сырой дневник — эпизодический источник, не автоматическая конституция, досье или список желаний. Не предполагать отдельную автоматическую запись каждого разговора.
4. `consolidate_context` — ручной запасной путь. В текущем коде нужна ролевая история `list[dict]` минимум из восьми записей. Сводка пишет `[контекст]` в журнал. В прямом `respond` изменение принадлежащего вызывающему коду списка может укоротить источник будущего контекста. В Telegram `voice_turn_envelope` передаёт снимок: локальное изменение не сокращает историю раннера и не освобождает следующий кадр. Читать результат, не обещать освобождение окна только по записи сводки.

Для непрерывности смотреть события/frontier/эпизод и source ids; для прочного факта — поддержанный claim и проекцию; для действия — run, receipt, git или artifact. Дневниковую строку считать подсказкой, пока происхождение не даёт ей больший вес. При изменении `tool_consolidate_context` пересмотреть этот снимок поведения.
