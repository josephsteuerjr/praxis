# Красный гейт требует причинной атрибуции

Падение проверки может быть связано с diff, baseline, окружением или расположением рабочей копии. Перед разрешённым override установить причину каждого неуспешного семейства, не стирать красное.

Примеры диагностических классов, не обещание текущего дефекта:

- `_SKIP_DIRS` исключает `.proposals`, а сама рабочая копия находится внутри такого каталога. Тогда `_corpus()` может оказаться пустым. Проверить фактический набор файлов; при необходимости сравнить тот же frozen commit в изолированном пути без исключения.
- `rails.manifest_drift()` сравнивает манифест с живыми значениями. Красный чистый checkout может наследовать несогласованный baseline. Сверить HEAD, содержимое и способ инициализации; не генерировать документ из неполного процесса ради зелёного.

Порядок:

1. Сохранить команду, HEAD, roster, исходный лог и environment без секретов.
2. Сравнить тот же тест на точном baseline в отдельной тестовой среде с тем же раннером.
3. Если причина неясна, проверить одну различающую гипотезу: путь, discovery, состояние fixture или окружение.
4. Сохранить точные id и causal diff результатов. Baseline RED не становится общим PASS.

`praxis_test.py` обеспечивает свой тестовый контракт; голый unittest или pytest может быть неэквивалентен. Но и официальный раннер не отменяет чтение результата.

Override допустим лишь по действующей процедуре и полномочиям с названными причинами и рисками; совпадение с baseline само по себе не разрешает merge. Не трогать живой проект для сравнительного теста.
