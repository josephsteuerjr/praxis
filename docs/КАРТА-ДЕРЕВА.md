# Карта дерева Hélène

Материал для человеческих описаний (онбординг, вкладка «Система», сайт).
Здесь — что есть в системе, кто с кем говорит и что происходит с сообщением.
Внутренние имена файлов даны в скобках, чтобы любую строку можно было
соотнести с кодом; в текстах для людей их можно опускать.

Из этого файла пишут тексты для покупателей, поэтому имена в нём обязаны
совпадать с кодом. Сверено с кодом 03.09.2026; разделы 1 и 10 (служба, режим
агента, брокер прав) пересверены 04.09.2026 — дважды: второй раз после того, как
владелец уточнил модель («режим — про ограду рук, служба — опция поверх неё»).
До первой сверки документ носил
имена поколения «Пульт» (pult.exe, praxis-svc.exe, pult.json, wizard.html) и
называл вкладку «Система» вкладкой «Устройство».

## 1. Из чего состоит продукт

Поставка — одна папка, пять частей:

| файл или папка | что это |
|---|---|
| `helene.exe` | приложение: окно, значок у часов, запуск всего остального |
| `runtime/` | собственный Python со всеми библиотеками (и `bash.exe` для инструмента командной строки) — на машине ничего не нужно |
| `app/` | сервер данных для окна (`deskapp.py`) и исполнитель агента (`localharness/`) |
| `tree/` | код самого агента — тот же, которым живёт агент автора на сервере, не упрощённая копия |
| `data/` | всё, что агент помнит и чем является: память, характер, журналы. Перенос агента = перенос этой папки |

Работают три программы:

1. **Приложение** (`helene.exe`, Rust) — окно без рамки и значок у часов.
   Закрыть окно — агент продолжает жить в фоне; настоящий выход — из меню
   значка. При запуске приложение поднимает две другие программы дочерними
   процессами, а если агент уже запущен (второй запуск, служба) — просто
   подключается к нему.
2. **Сервер данных** (`app/deskapp.py`) — читает файлы агента и отдаёт их
   окну: переписку, ходы, контекст модели, ошибки. Пишет он ровно в три места,
   и это не «только чтение»: сообщения из поля ввода и с телефона (файлами в
   почтовый ящик исполнителя, `memory/.control/desk_inbox/`), список спаренных
   телефонов (`memory/.state/devices.json`) и правку маркдауна из окна —
   конституцию, навыки, заметки (`POST /api/md` через `readers.safe_write_md`:
   только `.md`, только внутри разрешённых групп, запись атомарная).
   Окно общается с ним по WebSocket-соединению (протокол `frame.desk.v1`);
   то же соединение умеет работать с агентом на удалённом сервере — окно
   разницы не видит.

   Кто пускается: сначала проверяются `Host` и `Origin` (чужая страница из
   браузера получает 403 и не получает CORS-заголовков), потом ключ. Ключ окна
   («владелец») открывает всё; ключ спаренного телефона («устройство») — только
   переписку и отправку слова, но не анатомию с ключом модели и не правку
   маркдауна. Ключ владельца — секрет дерева (`memory/.state/desk-token`): его
   заводит тот, кто первым поднял харнесс (окно или служба), и предъявляют оба.
   Без ключа не пускается никто, даже по петле: иначе владельцем трубы был бы
   любой процесс этой машины и любая другая учётная запись Windows. В текстах
   для покупателей фразу «только чтение» про этот сервер не употреблять: он
   пишет, просто пишет ровно перечисленное выше.
3. **Исполнитель** (`app/localharness/runner.py`) — единственный, кто
   *запускает* агента. Слушает два источника: сообщения из окна (файлы в
   `data/memory/.control/desk_inbox/`) и Telegram (если настроен бот). На
   каждое обращение запускает один ход агента — строго по одному, потому что
   агент один.

Опционально четвёртая — **служба Windows** (`helene-svc.exe`): она поднимает
сервер данных и исполнителя, и агент живёт без открытого окна. Служба — не
режим агента, а опция поверх любого из них (раздел 10). Делает она это
не под собой: служба запускает отдельный процесс `helene-svc.exe session-host`
**в сессии владельца**, задачей планировщика `Helene\session-host`, заведённой
на владельца и без повышения прав. Так агент работает правами человека и видит
рабочий стол — из нулевой сессии Windows рабочего стола не видно вовсе. Плата
за это честная: **до входа владельца в систему служба агента не поднимает**,
поднимать его тогда некуда. Приложение при живой службе становится её клиентом.
Сверх этого служба выравнивает права на папку установки при каждом старте и
держит трубу брокера прав для окна — см. раздел 10.

## 2. Путь сообщения (главный процесс)

Что происходит между «человек нажал Enter» и «пришёл ответ»:

1. **Приём.** Сообщение из окна падает файлом в почтовый ящик исполнителя;
   сообщение из Telegram приходит длинным опросом Bot API (`botapi.py`).
2. **Сначала память, потом мысль.** Реплика записывается в память агента ДО
   того, как он начнёт думать: в ленту комнаты (`data/memory/groups/…`) и в
   события жизни (`data/memory/life/…`, модуль `memory_life.py`). Правило
   дерева: восприятие пишет, контекст читает.
3. **Сборка контекста** (`frame_shadow.py`). Всё, что модель увидит этим
   ходом, собирается из четырёх зон — см. раздел 3.
4. **Цикл хода** (`agent.py`, `voice_turn_envelope`). Модель думает,
   вызывает инструменты, смотрит их результаты и думает снова — столько
   поворотов, сколько нужно. Каждый вызов инструмента оставляет запись.
5. **Слово наружу.** Ответ человеку — это тоже инструмент (`reply`): агент
   вызывает его явно, и доставку выполняет транспорт — окно или Telegram.
   Квитанция называет канал и номер сообщения. Текст без вызова `reply` —
   внутренняя заметка, наружу не уходит.
6. **Конец хода — решение, а не тишина.** Ход закрывается инструментом
   `end_turn` с названным исходом (сделано / жду / не вышло). Из молчания
   конец не выводится.
7. **Следы.** После хода остаются: карточка хода со всеми шагами
   (`data/memory/runs/<месяц>/<ход>/`), строка в ленте прожитых ходов
   (`turns.jsonl`), запись о вызове модели с ценой и кэшем
   (`llm_calls.jsonl`). Окно рисует всё это из файлов.

## 3. Контекст модели: четыре зоны и почему это дёшево

Модуль `frame_shadow.py`. Всё, что модель получает на вход, разложено в
четыре зоны (внутреннее имя схемы — K‖E‖A‖T):

- **Характер** (зона K, файл `data/soul/SOUL.md`) — конституция агента:
  кто он, зачем, как говорит, чего не делает, кому верен. Единственный
  обязательный документ; пишется человеком и самим агентом. Не меняется
  никогда в течение эпохи.
- **Эпоха** (зона E) — замороженный снимок знаний агента о себе: какие
  инструменты есть, какие желания активны. Меняется только на названных
  границах (сменился набор инструментов, изменились желания) — тогда
  замораживается новая эпоха, и это видно в журнале.
- **Разговор** (зона A) — лента реплик. Только дописывается снизу.
- **Текущее** (зона T) — кто говорит и что пришло сейчас.

Зачем так: первые три зоны стабильны байт в байт, и провайдер модели кэширует
их как префикс. Платим по-настоящему только за хвост. На живых ходах из кэша
приходит 80–99 % входа — это видно в окне зелёной полоской у каждого вызова.

Каждая сборка контекста сохраняется слепком
(`data/memory/.state/shadow/<поток>/`) — вкладка «Контекст» показывает их дословно,
с разницей между соседними слепками: где префикс цел, где разошёлся.

## 4. Память: файлы, не база

Агент помнит файлами в `data/` — всё можно открыть и прочитать глазами.

| что | где | модуль |
|---|---|---|
| события жизни (каждая реплика, каждый факт) | `memory/life/events/*.jsonl` | `memory_life.py` |
| ленты комнат (переписка по чатам) | `memory/groups/*.jsonl` | пишет транспорт |
| дневник (агент пишет сам, инструмент `journal`) | `memory/journal/*.md` | `agent.py` |
| досье людей (`remember`) | `memory/people/` | `agent.py` |
| заметки по комнатам («сказала», «обещала») | — | `notes.py`, `promises.py` |
| желания — журнал намерений с причинной цепочкой | `memory/desires/` | `desires.py` |
| навыки — инструкции самому себе (`write_skill`) | `soul/skills/*.md` | `agent.py` |
| поисковый индекс по всему этому (`recall`) | `memory/.state/recall.sqlite3` | `memory_index.py` |
| граф связей людей и понятий | — | `graph.py` |

Про желания отдельно: это не список задач, а журнал только-на-дозапись с
причинной цепочкой «заметил → захотел → выбрал → сделал → увидел →
изменилось». Каждый шаг ссылается на ход, в котором случился, — намерение
можно проследить до фактов.

## 5. Ходы и надёжность

Каждый ход — это **прогон** с собственной папкой и журналом
(`run_manager.py`, `run_context.py`):

- каждый шаг (вызов модели, вызов инструмента, результат, доставка)
  записывается ДО того, как случится следующий;
- побочные эффекты (отправка сообщения) имеют ключи неповторения — при сбое
  и повторе ничего не отправится дважды;
- убили процесс посреди хода — при следующем запуске незавершённые прогоны
  находятся и честно закрываются или доводятся (`recover_durable_state`);
- у завершённого прогона есть итоговая запись и краткий пересказ (RECAP).

Правило всего дерева: **не выводить факты из тишины**. Не ответил — это
решение или сбой, и в журнале видно, которое из двух.

## 6. Инструменты

Инструмент — функция с именем, описанием и схемой аргументов (в дереве их
около сотни, собирает `offered_tools_for` в `agent.py`). Описание инструмента
— единственное «условие вызова»: модель сама решает, что позвать, читая
описания. Никакого скрытого планировщика нет.

Группы: память (recall, remember, journal, желания), разговор (reply,
end_turn, реакции), файлы и мастерская (чтение/правка/поиск, проекты,
запуск команд), командная строка (`shell` — в поставке работает через
собственный `bash` в `runtime/`), веб (чтение страниц, поиск — `webtool.py`),
почта (`mailer.py`), самонаблюдение (`my_capabilities` — честный снимок
собственных возможностей кодом, не по памяти модели), просьба о папке вне дома
(`mount_request`) и просьба о команде с правами (`broker_request`) — обе см.
раздел 10.

⚠ Один инструмент в списке есть, а работать ему нечем: `computer` — рука окон,
экрана, клавиатуры и мыши — обращается к телу агента-предка, которого в поставке
Hélène нет. Она отвечает об этом прямо, но в текстах для людей обещать «агент
видит экран и водит окна» нельзя ни для одного режима: порт UIA не сделан.

Вкладка «Система» показывает живой список с полными описаниями — те же
байты, что видит модель (`data/memory/.state/anatomy.json`, пишет исполнитель
при старте).

## 7. Транспорты: одна замена вместо целого мессенджера

В боевом дереве связь с Telegram держит модуль на девять тысяч строк
(`mtproto_runner.py`, личный аккаунт). В продукте он не используется вовсе.
Вместо него — один словарь функций доставки в `agent.py` (внутреннее имя
`_TELETHON`), который наполняют:

- `transport.py` — окно приложения: доставка в ленту, чтение своей комнаты;
- `botapi.py` — Telegram Bot API: длинный опрос входящих, отправка с резкой
  по лимиту, темы форумов как отдельные комнаты, реакции, файлы. Работает по
  одному токену от @BotFather — без номера телефона и личного аккаунта.

Агент не знает, кто именно доставляет его слова: он вызывает «отправить» и
получает квитанцию. Чего бот не умеет по правилам Telegram — историю чатов до
своего прихода, список чужих диалогов, первое сообщение незнакомцу — на то
инструменты отвечают честным отказом, а не имитацией.

Обе двери ведут в один организм: у окна и Telegram общая память, общий
контекст, общие желания.

## 8. Мозг

`llm.py`. Любой OpenAI-совместимый или Anthropic-совместимый сервис: адрес,
ключ и имя модели — три строки в `helene.json`. Локальные модели (Ollama,
LM Studio) подходят без ключа. Внутри: две роли (голос и вспомогательная
проверка исходящего), запасная модель на случай отказа, учёт токенов и кэша
по каждому вызову. Настройки мозга агент может менять и сам — инструментом
`switch_brain`; продукт не затирает его выбор при перезапусках.

## 9. Саморазвитие

Код агента — обычные файлы в `tree/`, и у агента есть инструменты правки
собственных файлов. В боевом дереве вокруг этого выстроен полный контур:
правка → проверочный прогон тысяч тестов → снимок для отката → перезапуск
(`selfdev.py`, `selfgit.py`, страж загрузки `bootguard.py`). В продукте v0
этот контур присутствует в коде, но проверочный прогон на машине пользователя
не разворачивается — честная граница: навыки, заметки и характер агент правит
свободно (это данные в `data/`), правки кода остаются на любителя.

## 10. Конфигурация, режим агента и служба

Один файл — `helene.json` рядом с приложением. Никаких скрытых настроек:
режим агента, местожительство харнесса, пути, мозг, Telegram, имя владельца.

⚠ **Два независимых измерения, а не один список из трёх.** Режим — про ограду
рук. Служба — про программу, ставится поверх любого режима и ограду не меняет.
В человеческих текстах их нельзя склеивать: пока служба считалась третьим
режимом, у владельца со службой и песочницей ограда снималась молча (закрыто
04.09).

**Режим агента** — один выбор владельца, который раскладывается в несколько
ручек; выбирается на экране установщика, меняется в «Настройках» → карточка
«Режим». Ключ `agent_mode`, два значения:

* **Песочница** (`sandbox`) — `shell` агента выполняется в контейнере Windows
  (AppContainer): читать ему выдан рантайм и код, читать и писать — дом агента и
  смонтированные папки; секреты владельца (`helene.json`, ключ модели, вход в
  подписку, сессия Telegram) закрыты и от `shell`, и от файловых рук. Выход
  контейнера в сеть — отдельным тумблером. Прав администратора не нужно.
* **Интерактивный** (`interactive`) — ограды нет: файлы и команды идут ровно с
  правами владельца, не больше. У ограниченной учётной записи агент ограничен
  так же. Права администратора продукт просит на конкретное действие, окном UAC.

Третье значение `service` писала первая редакция, пока службу считали режимом:
оно читается ради совместимости, оградой не считается и заменяется выведенной
оградой при первой же записи файла.

**Служба Windows** — галочка на том же экране, поверх выбранного режима.
Ставится один раз под администратором и даёт три вещи из раздела 1: жизнь без
открытого окна, выравнивание прав на папку установки, брокер прав. Стоит она или
нет — спрашивается у самой Windows, а не хранится выбором в файле. Внутри опции
две галочки: «разрешить агенту нулевую сессию» (`service.session0`, по умолчанию
выключена) — харнесс поднимается под самой службой, права системы без рабочего
стола, ею же открыта агенту дверь `exec` у брокера; «правило брандмауэра ставит
служба» (`service.firewall`, по умолчанию включена) — про кнопку «Телефон», прав
агенту не даёт. ⚠ Второй ключ сегодня записывается, но службой ещё не читается.

Правда о режимах живёт в одном месте — `localharness/modes.py`; установщик и
окно берут названия и описания оттуда, чтобы владелец не выбрал одно, а получил
другое. Ограда песочницы накрывает `shell` и файловые руки — и только их;
инструменты запуска программ и правки кода (`run`, `coding_*`, `pip_install`)
идут мимо неё, и в текстах для людей называть песочницу «клеткой для агента»
нельзя.

⚠ Ключ `mode` в том же файле — **не** про это: он говорит, где живёт харнесс
(`local` или `remote`). Два разных смысла у похожих слов, и в человеческих
текстах их надо разводить: «режим агента» и «местожительство харнесса».

**Монтирование** — единственная дверь агента наружу. Папку открывает владелец,
перечисляя её в `sandbox.mounts`; агенту она видна как `data/workspace/mnt/<имя>`
и работает в любом режиме, а не только в песочнице. Сам агент открыть папку не
может — он подаёт просьбу инструментом `mount_request` (полный путь и «зачем»
одной строкой), просьба ложится в `data/memory/.state/mounts.json`, решает
человек. Список читается на ходу, перезапуск не нужен.

**Брокер прав** живёт при службе: окно просит через него привилегированное
действие (сегодня одно — правило брандмауэра для телефона), служба выполняет и
возвращает квитанцию, каждое обращение ложится строкой в `data/broker.log`.

**Агент брокера не зовёт — он просит.** Рука `broker_request`
(`localharness/broker.py`) кладёт просьбу в
`data/memory/.state/broker-asks.json`; окно показывает её владельцу обычным
окном Windows — команду целиком и «зачем» словами агента, — и только по «да»
идёт в трубу своим токеном. Решение и квитанция уходят в
`broker-answers.json`, отказ записывается наравне с согласием, просьба старше
десяти минут отклоняется без вопроса. В человеческих текстах это надо называть
подтверждением, а не замком: брокер закрыт от чужих программ, а от самого
агента закрыт быть не может — в интерактивном режиме он читает тот же секрет.

Первый запуск
без явной квитанции `setup_complete` (или со старым непустым ключом) открывает
мастер настройки — отдельная программа `helene-setup.exe` (`setup/`), которая
пишет этот же файл. Явная
квитанция позволяет честно завершить настройку Ollama/LM Studio без фиктивного
ключа. Тонкие настройки дерева — переменные окружения,
которые исполнитель выставляет из блока `env` (`boot.py`); их реестр — три
сотни ручек, все с умолчаниями.
